# 0008: テストのモック境界を「層」ではなく「純粋性」で引く

## 背景

層ごとにテストを書き、層ごとに依存をモックしていた。テストは独立して速く、緑だった。

実装の変更が進むと、別の層に入った変更がモックに反映されず、**モックが古い契約のまま固定値を返し続ける** 状態が起きた。テストは通る。壊れているのは本番だけ。デグレを検知するために書いたテストが、モックの独立性ゆえにデグレを見逃していた。

原因は二つ重なっていた。

1. モックしなくてよい純粋な協力者（usecase、domain の関数）までモックしていた
2. モックが依存先の契約（インターフェース型）に縛られておらず、依存先の型が変わってもモックは古い形のまま通っていた

<!-- 要確認: 原文はここで欠落。2. の後半は background.md §3-2 の表から補った -->

対策は「モックを人が同期し続ける」ことではなく、**同期そのものを不要にするか、同期漏れをコンパイルエラーにする** ことである。

## 決定

モックするかどうかを「どの層か」ではなく **「純粋か不純か」** で決める。純粋な協力者（domain / usecase）は実物を呼び、不純な殻（DB・HTTP・時刻・環境変数に触れるもの）だけを差し替える。差し替える殻には次の条件を課す。

<!-- 要確認: 原文の表は A〜B 行と C 行の前半が欠落。background.md §3-2 の表と scripts/test-audit/README.md の条件定義から補った。D・E 行は原文のまま -->

| 条件 | 内容                                                                              | これが無いと起きること                                                       |
| ---- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| A    | 純粋なモジュール（domain / usecase）はモックしない。実物を呼ぶ                    | 実装が壊れてもモックは固定値を返し続け、テストは緑のまま本番だけ壊れる       |
| B    | 殻のモックは依存先のインターフェース型で縛る（`vi.fn<I["m"]>()` + `satisfies I`） | 依存先の型が変わってもモックは古い形のまま通る                               |
| C    | フィクスチャは手書きせず、依存先の factory から導く                               | 依存先の値の意味が変わってもフィクスチャが古いまま通る                       |
| D    | 各層は自層の責務だけをアサートする                                                | （偽パスではなく）下層の正当な変更で上層が落ち、テストの書き換えが常態化する |
| E    | 殻は契約テストで守り、CI で実インフラに対して流す                                 | モックの台本と実インフラの振る舞いがずれても単体では検知できない             |

E2E からは仕様検証の責務を剥がし、デプロイ後の導線の疎通確認（モックなし・到達のみ・導線ごとに一本）だけを残す。

流派としては古典派（Classical school）に属するが、これは選択の入力ではなく、出来上がった構造に外から付いた名前である。隔離基準は古典派の「実物が使いにくいもの」を「不純なもの」に置き換え、人の判断を関数の性質に機械化した。

## 前提

この決定はすべて、アプリケーション全体の設計が層ごとに責務と契約を持っていること（VO → Entity → Policy → Usecase → Entrypoint、依存は内向き）と、核が本当に純粋であることを前提にしている。domain や usecase の中に `new Date()` や DB 呼び出しが紛れ込むと「実物を呼ぶ」が「副作用を呼ぶ」になり、古典派の定番の弱点（遅い、非決定的）がそのまま現れる。時刻は境界で取得して核に引数で渡す。ID 採番だけは factory に閉じ、決定性が必要なテストではスタブする（[0001](./0001-domain-factory-clock-idgen.md)）。

## 理由

- 守りたいのは「入力に対して何が返るか」であり、協力者をどう呼んだかは実装の都合。呼び方を固定すると内部を組み替えるたびにテストが落ち、リファクタの摩擦がテストを書く動機を削る
- モックが得る「設計のフィードバック」は、層の構造と依存の向きを先に決めることで既に得ている。モックで協力者のインターフェースを発見する必要がない
- 純粋か不純かは関数が外界に触れるかで機械的に決まる。「これはモックすべきか」をレビューで議論する余地がなくなり、準拠を機械で測れる（`scripts/test-audit/`）

## 却下した案

- **層ごとに独立したモックを置き続け、人が同期する**: 背景の偽パスそのもの。同期漏れは検知できず、注意に依存する
- **ロンドン派（すべての協力者をモックし、呼び出しを検証する）**: 利点である設計フィードバックは層構造で代替済みで、弱点（偽パス、リファクタ耐性の低さ）だけが残る
- **E2E で仕様を検証する**: 純粋な核が分離されていれば、ルートテストが殻より内側の全層をミリ秒で通す。E2E に仕様検証を残す理由がなく、遅さと不安定さだけが残る

## 結果

**得たもの**

- ルートテストが殻より内側の全層をミリ秒で通す、プロセス内の結合テストを兼ねる。E2E から仕様検証を剥がせる根拠
- 層ごとにテストの意味が一つになる。Domain が落ちたら仕様、Route だけが落ちたら HTTP 契約、契約テストだけが落ちたら殻、スモークだけが落ちたら環境

**引き受けたもの**

- 下層が壊れると上層のテストも連鎖して落ちる。各層に自層のテストがあれば最も具体的な失敗は下層に出るので、局所化は保たれる
- 殻のモックが返す値は依然として「書いた人が信じている殻の振る舞い」。これは条件 E（Phase 2 の実 DB 統合）が入るまで偽パスの経路として残る
- 純粋性の規律が崩れると（核に `new Date()` や DB 呼び出しが紛れ込むと）古典派の定番の弱点がそのまま現れる。規律の維持は毎回の変更の判断であり、自動化されない

**残るリスク**

**測り方**

- 構造: `npm run test:audit`（条件 A〜E への準拠率、疑いの一覧）。`--strict` で A と型なし殻モックをゲートにする
- 検知力: `npm run test:mutation:domain`（mutation score。層ごとに別の基準、survived の中身を読む）
- 実績: 本番に漏れたデグレを「認知の外 / 偽パス（構造）/ 偽パス（殻）/ 配線・環境 / 仕様変更時の判断」で分類し、偽パス（構造）が 0 に収束することを確認する

再検討する条件: 偽パス（構造）が 0 に収束したあとも本番デグレが減らない場合、または核の純粋性を保つコストが層構造の維持コストを上回った場合。
