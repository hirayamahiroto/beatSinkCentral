# プロフィール API 設計（アーティスト情報）

> **このドキュメントの位置づけ**
>
> [`profile-information-design.md`](./profile-information-design.md) の情報設計をもとに、
> **詳細ページ表示 ＋ 登録（作成・編集・公開）**に必要な API を定義する。
> HTTP メソッド・URL の規範は [`../server-architecture/api-design-guidelines.md`](../server-architecture/api-design-guidelines.md) に従う（GET / POST のみ）。
>
> リクエスト/レスポンス型の詳細・認可条件は未決事項（§5）の確定後に詰める。**WIP**。

---

## 1. スコープ

| 含む                                                       | 含まない（後続・別スコープ）                       |
| ---------------------------------------------------------- | -------------------------------------------------- |
| 詳細ページの情報取得                                       | 一覧カード取得（`GET /artists`）                   |
| プロフィールの登録（作成・編集・公開切替）                 | AI Intro 生成 / 画像アップロード（Blob）           |
| —                                                          | 計測 API（計測はフロント側に置く → §4）            |

リソース名は `artists`（複数形・規範準拠）。

---

## 2. API 一覧

### 2-1. 詳細ページ側

| 操作     | メソッド | エンドポイント | 用途                       | 返す粒度                                      |
| -------- | -------- | -------------- | -------------------------- | --------------------------------------------- |
| 詳細取得 | GET      | `/artists/:id` | 詳細ページの全情報を返す   | 全項目（①属性 ＋ ②Story ＋ ③SNS）を 1 回で返す |

詳細ページは段階的開示で全レイヤーを 1 ページに載せる（「もっと読む」はインライン展開＝同一ページ）ため、**1 リクエストで全項目を返す**。

| 分類    | 項目                                | 画面上の段                  |
| ------- | ----------------------------------- | --------------------------- |
| ①属性   | 名前 / 画像 / タグライン / ジャンル | ファーストビュー（つかみ）  |
| ②Story  | Story 本文 / 活動情報 / ハイライト  | 展開（「もっと読む」の先）  |
| ③応援   | SNS リンク（複数）                  | 応援（ファネル終点）        |

### 2-2. 登録側

| 操作        | メソッド | エンドポイント         | 用途                                       |
| ----------- | -------- | ---------------------- | ------------------------------------------ |
| 作成        | POST     | `/artists`             | 新規登録（サーバーが ID 発行）             |
| 更新        | POST     | `/artists/:id`         | プロフィール編集（全項目の上書き）         |
| 編集用取得  | GET      | `/artists/:id`         | 編集フォームの初期値取得（下書き含む）     |
| 公開/非公開 | POST     | `/artists/:id/publish` | `published` フラグ制御                     |

> `GET /artists/:id` は、詳細ページ用（公開＝`published` のみ・誰でも）と編集用（下書き含む・本人のみ）を**認可によって出し分ける**想定。エンドポイント分割するかは未決（§5）。

---

## 3. 作成・更新のリクエスト項目

§3-2（情報設計）MVP 列に対応。

| 分類    | 項目                             | 型                   | 必須        |
| ------- | -------------------------------- | -------------------- | ----------- |
| ①属性   | 名前（活動名）                   | string               | ✅          |
| ①属性   | 画像                             | URL（外部URL指定）   | ✅          |
| ①属性   | ジャンル / スタイル              | string[]（自由入力） | ✅          |
| ①属性   | タグライン                       | string（短文）       | 任意        |
| ②Story  | Story 本文                       | text                 | ✅          |
| ②Story  | 活動情報（拠点 / 形態 / 所属）   | string               | 任意        |
| ②Story  | ハイライト（年×見出し・最大3件） | 構造化[]             | 任意        |
| ③応援   | SNS リンク                       | URL[]                | ✅（最低1） |

- 画像は**外部 URL 指定のみ**（Blob アップロードは後続）。
- ジャンルは**自由入力**（マスタ化は後続）。
- Intro（AI生成）は**受け付けない**（後続フェーズ）。

---

## 4. 公開（publish）の扱い

`published: false`（下書き）で作成・保存でき、**公開時に最小核が揃っているかを検証**する。

```
公開可能条件（MVP 最小核）：
  名前 / 画像 / ジャンル / Story / 活動情報 / SNS（最低1件）が揃っている
```

- 作成・更新は最小核が欠けていても**保存は許可**（書きかけを下書きとして保持）。
- `POST /artists/:id/publish` 実行時に最小核を満たさなければエラーを返す。
- ※ 正確な公開可能条件は情報設計 §6 で未決。上記を暫定とし、確定後に publish のバリデーションへ反映。

---

## 5. 計測（API ではない）

情報設計 §5-2 の通り、計測イベントは**フロント／エントリポイント側**に置く（ドメイン層・データ操作層に混ぜない）。専用の計測 API は作らない。Vercel Web Analytics ＋ 主要アクションのカスタムイベントで構成する。

詳細ページに仕込むイベント：

| 計測の意図       | イベント                                   |
| ---------------- | ------------------------------------------ |
| ②離脱 / ③閲覧深度 | 「もっと読む」展開（＝深掘り）             |
| ②離脱            | Story のスクロール到達度（どこまで読むか） |
| ③ファネル終点    | SNS リンクのクリック（外部遷移）           |

> 一覧→詳細の遷移計測（①アクセス量）は一覧カード側の責務（本スコープ外）。

## 6. 未決事項

- **公開状態の出し分け**：`GET /artists/:id` を認可で 1 エンドポイント出し分けにするか、編集用を別パス（例 `/artists/:id/edit`）に分けるか。
- **publish の形**：`/publish` 一本でトグル（公開↔非公開）にするか、`publish` / `unpublish` に分けるか。
- **所有モデル**：1 ユーザー 1 アーティスト制約を置くか、複数登録を許すか（認可・所有者判定に影響）。
- 公開可能条件の具体（情報設計 §6 と連動）。
- リクエスト/レスポンスの DTO 型・バリデーション・認可条件の詳細。
