## 1. 一次検証の本丸（再確認）

いま検証しているのは「**翻訳された背景（Story）は、シーンの外の人を来場まで動かすか**」（H3）。前提に H1（中堅層が書き切り、貼るか）と H2（告知経由で外の人が来るか）。詳細ページは検証の器であり、検証対象はページの完成度ではない。

## 2. 課題の再定義 — 認知の課題は 3 層に分かれる（うち 1 層は 2026-09 追加）

現行 PRD の課題「大衆からの認知の欠如」を、次の 3 層に分解する。

| 課題             | 中身                                                                                                       | 誰の損失か                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **言語化の課題** | 本人自身が「何を表現したいか（コンセプト）」を言葉にできていない可能性。これが無いと伝達も蓄積も始まらない | アーティスト本人（売り出し方が定まらない）                 |
| **伝達の課題**   | 名前は知られても「何を表現したいか（コンセプト）」が知られない。ライブ情報だけではコンセプトは伝わらない   | 大衆（判断材料が無い）とアーティスト（正しく理解されない） |
| **蓄積の課題**   | パフォーマンスは揮発する。ライブは消えもので、活動が資産として残らない                                     | アーティスト本人と、業界全体                               |

「名前だけ知られる」は design-core のジョブ三層の**表層**、「コンセプトごと理解される」は**中層**（自分の活動を正しく理解してほしい）に対応する。この分解は design-core の「力点は中層〜深層」と一致する — 課題がズレたのではなく深まった。

> この 3 層はまだ**仮説**。聞き取り①（§6 参照）で中堅層に当てて確かめる。「言語化の課題」は聞き取り①の追加2問（自分のコンセプトを言葉にできているか・したいと思うか、T00で確定しPRD §7-5へ反映済み）に対応するが、定量側の検証案は §6 に追記する（未合意）。

## 3. 中継機コンセプト — beatfolio の機能定義

> **beatfolio ＝ アーティストの活動を記録（folio）し、コンセプトを可視化して資産化し、そのコンセプトをライブ会場で経験してもらうための中継機。**

名前の由来もここに置く: beat（Beatbox）× folio（記録集・作品集）。記録を起点に、認知（知ってもらう）→応援へ結びつける。

```
        【知る】                【応援する】
  Story／翻訳／シグネチャーサウンド ──→ ライブ会場での体験
        ↑                              ↓
  世界観の変遷が見える ←── イベントごとの「色」の記録
        【資産（folio）】      【記録する】
```

PRD §2-4 の「公式の条件」4 つ（本人が定義した自分がある／消えない・転機が増えていく／外の人が理解できる／更新の起点）は、この中継機の性質の 4 分割にあたる。「エコシステムの一番の資産＝蓄積された活動情報」は design-core のフライホイールの資産面の言い直し。

### 3-1. 「知る→応援する」の転換チャネルは 3 つ

| チャネル     | 中身                                           | 現行の最小実装                               |
| ------------ | ---------------------------------------------- | -------------------------------------------- |
| 人           | Story（3 つの問い）                            | F1                                           |
| 価値の言語化 | 翻訳（運営の言葉）                             | F3                                           |
| **音**       | **シグネチャーサウンド（この人の代名詞の音）** | F4 聴きどころ（動画 1 本＋「ここを聴いて」） |

根拠は PRD §2-1「アイデンティティは音そのもの。文字より先に音で識別される」。音チャネルの拡張（名刺代わりの音の独立フィールド化）は二周目。

### 3-2. 記録の単位は「イベント出演」

- 資産の最小単位＝イベント出演（T05 のオファー行。終了後も消さず状態遷移で残す）。
- そこに「そのライブで何を表現したか（**色**）」が付くと、並べたときに世界観の**変遷**が読める。
- ベータでの最小形は F2 の一言（オファーの理由文）＝イベントに挑むスタンスの言語化。構造化はしない。

## 4. 時間軸の整理（周回モデル）

| 周回                         | 問い                                 | 装置                                                                                                 | 状態                              |
| ---------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------- | --------------------------------- |
| **一周目（ベータ 6〜8 週）** | 背景を読んだ外の人は来場するか       | Story＋翻訳＋聴きどころ＋オファー（理由文込み）                                                      | PRD・チケット T00〜T14 で定義済み |
| **二周目（成立後）**         | 記録が積もると公式性・再訪が強まるか | 過去イベントのアーカイブ（オファーの事後化）、色の変遷ビュー、シグネチャーサウンド、イベント後の記録 | 本メモで予約。未設計              |
| **三周目（Phase 2）**        | イベント単位の動線・オーガナイザー辺 | イベントページ・エントリー・告知基盤                                                                 | design-core に予約済み            |

- イベントごとに別 LP は作らない（URL 分散は「公式＝消えない一つの場所」と矛盾）。イベントページが要るのは三周目で、それは動線ではなく**記録＋合流点**になる。
- 実装への含意は 1 点のみ: オファーを「使い捨ての告知」ではなく「イベント出演の記録」として設計する — T05 で担保済み。

## 5. 現実世界との接続 — 「来場 → 記録 → 再訪」の帰り道

現行 PRD は「予習 → 来場」までの設計で、会場体験がページに還る帰り道が空いている。候補:

| 案                         | 中身                                                              | ベータでの扱い                                                       |
| -------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------- |
| **ライブ翌日の記録メール** | 受信登録者（F7）に翌日「昨日の記録（写真 1 枚＋一言）」を手動送信 | **採用候補**。H5（戻り道）を「次の告知」より早く検証できる手作業実験 |
| 会場からの導線（QR）       | 当日の物販・フライヤーにページ QR                                 | F6 告知素材（T13）に含める                                           |
| イベント記録ページ         | 終了したオファーが記録ページ化する                                | 二周目                                                               |

## 6. ベータへの反映提案（PRD 改訂候補・未合意）

1. **Story 第 3 問を「何を表現したいのか（コンセプト）」へ変更** — `profile-information-design.md` §6 と PRD §9-2 の未決「活動コンセプトを Story に内包するか」への答えにあたる。H1 の検証対象に自然に含まれる。
2. **聞き取り①に 2 問追加**: 「自分のコンセプトを言葉にできているか・したいと思うか」「過去のパフォーマンスが消えていくことを損失と感じているか」— §2 の課題再定義そのものを検証する。
3. **計測イベントに `listening_point_play` を追加**（§6-1 / T03）— 転換に効いたのが Story か翻訳か音かを、offer_click の前段行動として分解観察する。
4. **ライブ翌日の記録メール**（§5）を週次運用（T12・T14）に組み込む。機能化しない。
5. **「言語化の課題」（§2）の定量検証**（**未合意・2026-09 追加**）— 聞き取り①の追加2問（項目2）は定性側の検証。定量側は、新規イベントを追加せず `story_chapters` の既存カラムをそのまま使う:
   - 各章の `created_at` − アーティスト登録日時 ＝「書き始めるまでの時間」
   - 「始まり」章と「コンセプト」章の `created_at` の差 ＝ 他の章は書けてもコンセプトだけ時間がかかっていないか
   - `updated_at` が `created_at` から乖離している（＝書き直しが多い）章 ＝ 迷いのシグナル
   - measurement-infrastructure-design.md §7 Step4「ad-hoc SQL での編集レビュー」の範囲で検証する。これで足りない場合のみ、編集画面側の専用イベント（例: `profile_edit_started`）を新規の計測対象として別途検討する（現行 PRD §6-1 は公開ページ側の計測のみをスコープにしており、編集画面側は含まれていない）。

上記はいずれも北極星（ビートボクサー以外の来場者数）と H1〜H6 の構造を変えない。
