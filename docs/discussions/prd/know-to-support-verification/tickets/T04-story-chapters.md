# T04: Story の章構造化（3 つの問い）

| 項目 | 内容                      |
| ---- | ------------------------- |
| 対応 | F1, H1 / PRD §5-1, §10    |
| 種別 | 作る                      |
| 依存 | T00（問いの内包判断）     |
| 規模 | L（**クリティカルパス**） |

## 背景

H1（供給）の器。現状の `artist_profiles.story: text` を、3 つの問い（始まり／転機／いま）に答える `StoryChapter[]` へ拡張する。ベータ週 1 の Story 執筆開始までに、書ける状態（構造＋編集画面）が要る。

## スコープ

### やること

- **DB**: `story_chapters` テーブル（1:N。`artist_profile_id` fk / `question_code` fk→問いマスタ / `body` / 並び順）。多値を JSON にしない（DB 設計方針）
- **問いはマスタ参照**: `story_questions`（`code` / `label` / 並び順）を持ち、UI にハードコードしない（checklist §14。語彙の出所は DB → BFF で解決 → props で UI へ）
- **ドメイン**: `StoryChapter` VO / entity 拡張 / behaviors。`ensurePublishable` の「Story 必須」を章構造でどう判定するか更新（例: 最初の問いに本文があること）— 条件変更は `profile-information-design.md` §3-4 と同時更新
- **編集画面**: 問いごとの入力。途中保存可（既存の保存/公開分離に乗る）
- **既存データの移行**: 既存 `story: text` の扱い（最初の章へ移すか、併存期間を置くか）を決めて migration に含める
- **表示**: 最初の章は常に表示、残りは展開（§5-2 順 2）。展開は T03 の `story_expand` 発火点になる

### やらないこと

- 見本文の同梱（§7-6: 書いてもらう前に見本を渡さない）
- 翻訳・聴きどころ（T06・T07）

## 受け入れ条件

- [ ] 3 つの問いに個別に答えて途中保存でき、公開条件が章構造で判定される
- [ ] 問いの文言が DB 由来で、`packages/ui` に文字列が直書きされていない
- [ ] 既存プロフィールの `story` が失われない移行手順がある
- [ ] VO / behaviors / policy / usecase / repository すべてに `index.test.ts` がある

## 着手前に決めること

- 「活動コンセプト」を「いま目指していること」の問いに内包するか（T00 / PRD §9-2）
- 旧 `story` カラムを残すか落とすか（並行更新ポリシー・ロールバック観点）
