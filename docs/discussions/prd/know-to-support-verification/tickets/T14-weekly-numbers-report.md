# T14: 週次の数字の返し（SQL → 定型文）

| 項目 | 内容                        |
| ---- | --------------------------- |
| 対応 | F8, H1, H6 / PRD §5-1, §7-3 |
| 種別 | 手作業（運用）              |
| 依存 | T03（イベントが流れてから） |
| 規模 | M（週次の反復）             |

## 背景

アーティストに数字が返ることが、続ける理由（H1）と紹介（H6）の駆動力（PRD §2-3 の (a)）。ダッシュボードは**作らない**。ad-hoc SQL と定型文で週次に返す。

## スコープ

### やること

- **SQL クエリ集**（このディレクトリにファイルとして残し、毎週使い回す）:
  - 開いた人数（`profile_view`、`from` 別内訳）
  - 読んだ割合（`story_expand` 率・最終章到達率・`story_scroll` 分布）
  - オファーを踏んだ人数（`offer_click`、`position`＝読む前／読んだ後の別）
  - 非ビートボクサー率（`survey_answer`）
  - 受信登録数（`notify_subscribe`）／招待の発生（`invite_open` / `invite_signup`）
  - T10 の登録者取り出し（手動メール送信用）
- **定型文テンプレート**: 数字 4 つ（開いた／読んだ／踏んだ／外の人の割合)＋一言。アーティストがそのまま受け取れる形
- **運営側の週次記録**: §6-3 の指標表（書く・貼る／発見／知る／応援／続ける）を週ごとに埋める台帳
- bot・運営自身のアクセスの除外条件をクエリに含める

### やらないこと

- ダッシュボード・可視化ツール（§5-3）
- アーティスト本人が見る画面（返しは運営からの連絡で渡す）

## 受け入れ条件

- [ ] クエリ集だけで §6-3 の週次指標がすべて出せる
- [ ] 1 人分の返しの作成が 15 分以内で回る
- [ ] 月次判断（§8）に使う「読んだ後の来場 vs 読む前の来場」の照合手順（イベント × 来場確認 §6-2）が書かれている
