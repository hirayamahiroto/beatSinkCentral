## 背景

PRD は discussions（未合意）にあり、既存規範と複数箇所で分岐する。CLAUDE.md の規約上、実装判断の根拠にできるのは `product/` と `architecture/` のみ。着手前に分岐を合意し、実装に必要な最小限を規範へ反映する。

## スコープ

### 決めること

1. **PRD 本文の合意**（特に §3 到達地点＝来場、§5-1 の F1〜F9、§5-3 非対象）
2. **計測基盤の L2 選択**: 自前 `analytics_events` か PostHog か（[`measurement-infrastructure-design.md`](../measurement-infrastructure-design.md) §8）。PRD §6 は自前を前提に書かれている
3. **計測 API の規範文言**: 「専用 API は作らない」との差分（同 §6）。取り込みルートをエントリ層に置くことの可否
4. §9-2 のうちベータ実装に影響するもの:
   - オファーが無い期間の主 CTA（フォロー／共有／動画）の優先順位 → T08 が待つ
   - 前室（ストーリーズ形式）を置くか → 置かない場合 T08 のスコープから外れる
   - 「活動コンセプト」を「いま目指していること」の問いに内包するか → T04 が待つ

### 反映すること（合意後、PRD §10 の表に従う）

- `profile-information-design.md` §3・§4（Story 章構造・翻訳・聴きどころ・オファー・段階的開示の順）
- `measurement-infrastructure-design.md` §5（イベントと props の追加）
- `flow-design.md` §2-1・§3-1 と `design-core.md` の Support 定義は、**ベータの結果を待ってから**でも実装は進められるため、先送り可（§10 は「合意後に反映」）

### やらないこと

- ベータの結果に依存する判断（事業の重心 A/B、一覧公開の条件）
