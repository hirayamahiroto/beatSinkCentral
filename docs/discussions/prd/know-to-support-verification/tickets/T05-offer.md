## 背景

応援（来場）の受け皿。時限で差し替わり、無い期間は区画ごと非表示（PRD §1-1 用語・§5-2）。共演者は H6（紹介）の起点で、T11（招待リンク）の前提。

## スコープ

### やること

- **DB**: `offers` テーブル（`artist_profile_id` fk / 日付 / 場所 / チケット URL / 一言 / 状態）＋ `offer_performers`（1:N。登録済みアーティスト参照 or 未登録の表示名）
- **ドメイン**: Offer entity / VO（日付・URL 検証）。「有効なオファー」の判定（開催日を過ぎたら表示対象外）は純粋関数としてビジネスロジック層に置く
- **編集画面**: 本人が次のライブを入力できる最小フォーム（共演者の追加を含む）
- **表示への引き渡し**: 詳細ページ（T08）が「オファーあり／なし」でレイアウト状態を切り替えられる形で BFF から返す。「あり／なし」は BFF が解決済みの形で渡し、UI 側で日付判定しない
- **チケット URL は外部送り出しのみ**（決済・販売は作らない）

### やらないこと

- 招待コードの発行・追跡（T11）
- オファー履歴の一覧表示・過去オファーのアーカイブページ
- 通知・リマインド

## 受け入れ条件

- [ ] オファーの登録・編集・（開催後の）自然な非表示ができる
- [ ] オファーが無い期間、詳細ページに空の区画が出ない
- [ ] 共演者は「登録済み＝プロフィールへのリンク」「未登録＝名前のみ（T11 で招待に差し替え）」の 2 状態を持てる
- [ ] 未取得と「オファーなし」が型で区別される（`null` 初期値、checklist §11-3）
- [ ] 各 module に `index.test.ts` がある

## 着手前に決めること

- 同時に有効なオファーは 1 件か複数か（PRD は「次のライブ」単数想定 → 1 件を推奨）
- User と Offer の権限（本人のみ編集。運営代行入力を許すか）
