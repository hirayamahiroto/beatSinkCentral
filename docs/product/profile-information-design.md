# プロフィール情報設計（アーティスト情報）

> **このドキュメントの位置づけ**
>
> beatfolio の**プロフィール（アーティスト情報）の情報設計**を定義する。
> 「何を・どう載せ・どこで見せるか」を、**プロダクトビジョンから逆算**して決めることを目的とする。
>
> 戦略・競合分析・ポジショニングの検討経緯は本体ではなく **付録**に要約する（情報設計の根拠として参照）。
> 既存の規範 [`phase0-flow-design.md`](./flow-design.md) と一部分岐している（StoryLine→Story、名鑑→発掘の方向）。**WIP**。合意項目を追って規範へ反映する。

## 1. ビジョンとの照らし合わせ（出発点）

情報設計は恣意的に決めない。**ビジョンが「プロフィールに何を要請するか」から逆算**する。

### 1-1. 北極星（最終ゴール）

**Beatbox 界の持続可能なエコシステムを作る** —— アーティストにお金が還元され、稼げる状態を生む。

```
持続可能な業界（お金が還元される）
  └─ 中核の柱 = アーティスト
       ├─ 課題：育っても支出ばかり → ステージに立たなくなる
       │        → やる意味を失う → スキルが活きない
       └─ 解決方向：良いパフォーマンス → 還元される仕組み
                  ＋ 無名でも日の目を浴びる可能性の提供
```

### 1-2. ビジョンがプロフィールに要請すること（逆算）

| ビジョンの要素                           | プロフィールへの要請（＝情報設計の制約）                                            |
| ---------------------------------------- | ----------------------------------------------------------------------------------- |
| 無名が「知られる」状態を作る             | **初対面の人にバックグラウンドが伝わる**こと。SNS bio では出せない深さを持つ        |
| 無名でも日の目を浴びる                   | 一覧で**発見され**、詳細で**引き込まれる**動線。埋もれない情報配置                  |
| 中核はアーティスト／実績が薄くても戦える | 実績の羅列でなく、**物語（Story）で価値を伝えられる**器。新人でも書ける項目         |
| いずれ「応援 → お金の還元」へ繋ぐ        | 今は「知る→理解する→応援(SNS遷移)」の動線を作り、**機能するか計測できる**状態にする |

> **差別化の核**：他では語られていない**バックグラウンド（Story）**を知れる場所。
> 名鑑型（属性データの列挙）ではなく、物語で「知る→理解する→応援する」を駆動する。

### 1-3. 現在地（このフェーズのスコープ）

> エコシステム基盤への投資の第一歩 ＝ **アーティスト情報を登録し、バックグラウンドが最低限わかる状態で公開でき、その閲覧・操作を計測できる**ところまで。
> マネタイズ・収益還元・AI Intro・特集編集は**将来フェーズ**。

## 2. 情報設計の原則

ビジョンの要請（§1-2）から導かれる、本プロフィール共通の原則。

1. **段階的開示（Progressive Disclosure）** — 一度に全部見せない。つかみ → もっと読む → 物語。年表のベタ表示はしない。
2. **属性と Story を分ける** — 短い事実（一覧で効く）と、物語（詳細で効く）を別レイヤーに。
3. **バックグラウンド最優先** — 差別化は「他で語られない背景」。Story を情報の中心に置く。
4. **実績ゼロでも成立する** — 新人でも書ける項目で構成する（受賞歴・再生数を必須にしない）。
5. **計測できる形に** — 動線の各段（発見・深掘り・外部遷移）にイベントを仕込めるよう情報と導線を設計する。

## 3. プロフィール情報の定義（中核）

### 3-1. 情報の 3 分類

| 分類            | 性質               | 動線     | 役割                                                                                     |
| --------------- | ------------------ | -------- | ---------------------------------------------------------------------------------------- |
| ① 属性（事実）  | 短い・一覧で効く   | 知る     | 発見のフックと最小の文脈                                                                 |
| ② Story（物語） | 物語・感情移入の核 | 理解する | バックグラウンドを伝える＝差別化の中心                                                   |
| ③ 応援導線      | 外部送り出し       | 応援する | ファネル終点。オファー（在る期間）／SNS・次の告知登録（無い期間）（検証ベータ PRD 準拠） |

### 3-2. フィールド定義

| 分類    | 項目                                               | 型                                                                                        | 必須                       | MVP       | 意図（なぜ載せるか）                                                                                                                  |
| ------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| ①       | 名前（活動名）                                     | string                                                                                    | ✅                         | ✅        | 識別・OGP・一覧                                                                                                                       |
| ①       | 画像                                               | URL（アップロードで発行）                                                                 | ✅                         | ✅        | 第一印象。一覧/OGP/詳細で使う。Supabase Storage へ直接アップロードし public URL を保存                                                |
| ①       | ジャンル / スタイル                                | string[]（自由入力）                                                                      | ✅                         | ✅        | 文脈。Beatbox 内のスタイル軸                                                                                                          |
| ①       | タグライン                                         | string（短文）                                                                            | 任意                       | ✅        | 1行のつかみ。OGP description                                                                                                          |
| ②       | **Story（3 章構造）**                              | `StoryChapter[]`（問い＋本文。3 問固定: 始まり／転機／何を表現したいのか）                | ✅                         | ✅        | **中核**。他で語られない背景・歩み。始まりの章は常に表示、残りは展開（検証ベータ PRD F1）                                             |
| ②       | 翻訳段落                                           | string（一段落）                                                                          | 任意                       | ✅        | 運営が「この人の何が凄いか」を書く。API は作らず運営が SQL で直接書く（検証ベータ PRD F3）                                            |
| ②       | 聴きどころ                                         | { videoUrl: string; comment: string }                                                     | 任意                       | ✅        | 動画 1 本＋「ここを聴いて」の一言（検証ベータ PRD F4）                                                                                |
| ②       | 活動情報（拠点 / 形態 / 所属 など）                | string                                                                                    | 任意                       | ✅        | 軽い事実。Story の補助                                                                                                                |
| ②       | ハイライト（年×見出し・最大3件）                   | 構造化（任意）                                                                            | 任意                       | △         | 任意の深層。年表化は避け数件に絞る                                                                                                    |
| ③       | オファー（日付・場所・チケット URL・一言・共演者） | 構造化（時限・同時有効1件）                                                               | 任意                       | ✅        | 応援導線の主。無い期間は区画ごと非表示（検証ベータ PRD F2）                                                                           |
| ③       | SNS リンク（複数）                                 | URL[]                                                                                     | ✅（最低1）                | ✅        | 応援導線。オファー不在期は主 CTA（検証ベータ PRD 参照）                                                                               |
| ③       | 「次の告知を受け取る」（メール登録）               | string（メールアドレス）                                                                  | 任意                       | ✅        | 戻り道。再訪のための受信登録（検証ベータ PRD F7）                                                                                     |
| 制御    | published（公開フラグ）                            | boolean                                                                                   | —                          | ✅        | 公開/非公開の制御。最低項目が揃って公開可                                                                                             |
| 制御    | 表現パターン（コンセプトページの見せ方）           | マスタ参照（`presentation_patterns.code`: interview / zoom_dive / spotlight / editorial） | 任意（未選択は interview） | ✅        | Story を没入型で読ませる `/players/[handle]/concept` の見せ方を本人が選ぶ。どの UI で描くかを DB に記録し、計測・切り替えの単位にする |
| ①(後続) | **Intro（約100字・AI生成）**                       | text                                                                                      | —                          | ✕（後続） | つかみの自動生成。**計測で効果を見てから投資**                                                                                        |

> **MVP の最小核**：名前 / 画像 / ジャンル / Story / 活動情報 / SNS リンク（＋ published）。
> 「バックグラウンドが最低限わかる」を満たす最小セット。

### 3-3. 後続に回す情報（理由つき）

| 項目                 | 後続にする理由                                          |
| -------------------- | ------------------------------------------------------- |
| AI Intro 生成        | まず静的ページの効きを計測 → 投資判断（ship + measure） |
| ジャンルのマスタ化   | 当面は自由入力。語彙が見えてから固定化                  |
| ハイライトの本格運用 | Story で代替可能。必要性を計測で確認                    |

> 画像アップロードは当初「外部 URL で MVP は足りる」として後続に回していたが、
> セキュリティ観点（任意外部 URL の露出）から Supabase Storage への直接アップロードとして対応済み
> （方式は [`../architecture/server/database/storage.md`](../architecture/server/database/storage.md) を参照）。

### 3-4. 公開可能条件（published を立てられる条件）

**保存（下書き）と公開は別の行為**として扱う。保存はいつでも部分的な内容で行え、公開は下記が全て揃ったときにだけ行える。

| 項目           | 公開に必須                                     | 補足                                        |
| -------------- | ---------------------------------------------- | ------------------------------------------- |
| 名前（活動名） | ✅                                             |                                             |
| 画像           | ✅                                             | 一覧 / OGP で必ず使うため                   |
| Story          | ✅（始まりの章は必須。転機／コンセプトは任意） | 中核。これが無い公開に価値がない            |
| ジャンル       | ✅（最低1）                                    |                                             |
| SNS リンク     | ✅（最低1）                                    | 応援導線の終点                              |
| タグライン     | —                                              | §3-2 の通り任意。OGP は画像・名前で成立する |
| 活動情報       | —                                              | Story の補助であり必須にしない              |

この条件の**唯一の規範はドメイン層の `ensurePublishable`**（`apps/api-server/src/domain/artistProfiles/policies/publishability`）とする。
フロントのフォーム検証は「同じ条件を先に案内する」ためのものであり、条件を独自に足さない・緩めない。条件を変えるときは本節とドメインを同時に更新する。

未達で公開しようとした場合、ドメインは不足項目（`missingFields`）付きで拒否し、UI は「あと何が足りないか」として提示する。

## 4. 動線における情報の配置

「どの情報を・どの画面で・どこまで見せるか」を段階的開示で配置する。大衆向け詳細ページの区画順は検証ベータ PRD §5-2 に従う（7 区画）。

```
[一覧カード] ← ①属性のみ
  画像 + 名前 + タグライン + ジャンル
        │ クリック（＝知る→理解するへの遷移を計測）
        ▼
[詳細ページ・7 区画（PRD §5-2）]
  1. 引っかかり（画像・名前・タグライン・ジャンル）
  2. 人（Story 3 章。始まりは常時表示、残りは展開）
  3. 翻訳（運営記入）
  4. 聴きどころ（動画＋一言）
  5. いま／一つの行動（オファー、または フォロー＞共有＞動画 の順の主 CTA）
  6. 戻り道（次の告知を受け取る・補助 SNS）
  7. 繋がり（オファーの共演者）
```

| 画面       | 見せる情報                       | 見せない情報                           |
| ---------- | -------------------------------- | -------------------------------------- |
| 一覧カード | 画像・名前・タグライン・ジャンル | Story・翻訳・聴きどころ・オファー・SNS |
| 詳細ページ | 上記 7 区画すべて（PRD §5-2）    | 任意項目が空の区画は非表示             |

- 「もっと読む」は**インライン展開**を推奨（SEO/OGP は本文同一ページが有利。離脱させない）。
- 一覧に Story を出さないことで、詳細への遷移＝「興味を持った」シグナルとして計測できる。
- 告知経由訪問者向けの前室（ストーリーズ形式）はベータでは作らない（T00 確定。検証ベータ PRD §5-2）。

## 5. MVP で作る情報範囲と計測

### 5-1. 公開する情報範囲

§3-2 の MVP 列（✅）。応援導線は**オファー（在る期間）／フォロー・共有・動画・SNS リンク（無い期間）**（検証ベータ PRD §5-2 で拡張）。

### 5-2. 計測設計 ★今回の肝

**目的（何を達成するための計測か）**：直近は**アーティストの認知を広げる**ため、まず「どこに関心が集まり・どこで離脱し・どこまで読まれるか」を掴む。これが**特集・情報発信の判断材料**になる（→ 北極星：認知拡大）。

**設計の順序**：「何を計りたいか（意図）」を先に決め、**その後に**数値・イベントを設計する。数値から入らない（測ること自体の目的化を避ける）。

#### この段階で計りたいこと（計測の意図）

| 意図         | 知りたい問い                             | 特集・情報発信への活かし方                 |
| ------------ | ---------------------------------------- | ------------------------------------------ |
| ① アクセス量 | どのアーティスト/ページに人が来ているか  | 関心が集まる人・発掘候補を特集に選ぶ       |
| ② 離脱       | どの段階で離れるか（一覧 / 詳細の途中）  | 離脱が多い段階を強化（つかみ・物語の補強） |
| ③ 閲覧深度   | Story のどこまで読まれ、何が読まれないか | 読まれる題材・人を特集の切り口にする       |

#### この段階の性格：探索（学習）であって最適化ではない

「そもそも何を発信すべきか・誰が刺さるか」を**学ぶための観察**。閾値で最適化する（例：応援遷移率が低ければ Story を直す）のは後の段階。今の計測が駆動するアクションは **「特集の題材・方向を決める」** という編集判断。

#### 設計原則

- 計測イベントは**フロント／エントリポイント側**に置く。ドメイン層・データ操作層に混ぜない（責務分離）。
- Vercel 環境に素直な構成を優先（Web Analytics ＋ 主要アクションのカスタムイベント）。具体ツールは実装時に確定。
- 数値・率（詳細到達率／深掘り率／応援遷移率 等）の具体設計は **後続ステップ**（意図確定の後）。

> 実装タスク（イベント実装・配線）は本書ではなく #165 ／ [`roadmap.md`](../plans/phase1-player-introduction/roadmap.md) 側に展開する。

## 付録 A. 競合・参照分析（情報設計の根拠）

既存の公人プロフィールを調査した結果。詳細所見は検討時の記録。

| サービス                         | 型         | 所見                                                                                     |
| -------------------------------- | ---------- | ---------------------------------------------------------------------------------------- |
| ソフトバンクホークス（選手名鑑） | 純・名鑑型 | 属性データのみ。物語ゼロ＝「既存ファンの参照」用                                         |
| ワタナベエンターテインメント     | 名鑑型     | 画像+名前グリッド。ストーリーは別セクションに分離されプロフィールに繋がらない            |
| hololive（タレント紹介）         | ハブ型     | キャッチフレーズ・キャラ設定・Q&A・SNS導線。**唯一「知らない人を引き込む」をやれている** |

**示唆**：名鑑が退屈なのは「既にその人を知るファンの参照」を解いているから。焚き付ける必要がない（別エンジンがある）。hololive が引き込めるのは、物語の引っかかり＋背後のコンテンツ機械があるから。
→ **無名アーティストにはその機械がない。だからプロフィール＋物語（Story）が発見装置にならざるを得ない** ＝ 本プロフィール設計が Story を中核に置く根拠。

**抜き出した設計の型**（hololive より）：1行のキャッチ（→タグライン/将来のIntro）／記憶に残る具体（→Story）／段階開示（→もっと読む）／外部への導線（→SNS）。

## 付録 B. ポジショニング検討（情報設計の根拠）

- 「良いプロフィールページの出来」は moat にならない。moat は **特定シーン（Beatbox）を掘って物語化する編集力**の側にある（将来）。
- 向かうモデルは名鑑型ではなく **発掘プラットフォーム／編集メディア × アーティスト DB**。参照：**Swissbeatbox**（メディア×コミュニティ×大会 GBB）。
- ターゲット仮説：**無名〜駆け出しの Beatbox アーティスト** × **Beatbox を掘るファン**。
- 「焚き付けは静的ページからは生まれない（量とコミュニティから生まれる）」は要検証の前提。だから**まず計測**して、特集・AI Intro 等の投資是非を判断する。

> この付録の各項目は「プロフィールに Story を中核として持たせ、計測を仕込む」という本体の情報設計判断の**根拠**であり、編集メディア化・マネタイズ自体は本フェーズのスコープ外。
