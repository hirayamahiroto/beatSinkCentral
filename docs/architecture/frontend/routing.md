# 画面 URL 設計（ルーティング）

> **位置づけ**
> 本ドキュメントは **beatfolio の画面 URL（ユーザーが辿る遷移）の設計方針**を定める。
> BFF の `/api/*` ルート設計は [`bff.md`](./bff/design.md) を参照。両者の対応関係は原則6で規定する。
> API（api-server）の URL 設計は [`../server/api-design-guidelines.md`](../server/api-design-guidelines.md) を参照。

---

## 第1部: ストラテジー（設計思想）

### URL は情報設計であって、実装の都合ではない

beatfolio は画面遷移で成り立つアプリであり、**URL はユーザーが辿る導線そのもの**である。
ディレクトリ構造の都合や実装順序で URL を決めない。「何が実体で、何がその実体に対する操作か」を先に決め、それを URL に写す。

### 原則1: 実体を先に URL へ置く

**公開されるもの（実体）の URL を先に決め、編集画面はその実体に対する操作として表現する。**

編集画面だけが先に存在し、編集対象の実体が URL 上に無い状態を作らない。実体の置き場が無いまま編集画面を置くと、その画面はどの階層にも属せず宙に浮く。

beatfolio における実体は **アーティストの公開プロフィール**である。これがプロダクトの中心価値であり、`/players` の一覧から辿る先にあたる。

### 原則2: パスは名詞（実体）、操作は動詞のサブパス

| 種別         | 表現       | 例                        |
| ------------ | ---------- | ------------------------- |
| 実体         | 名詞       | `/players/[accountId]`    |
| 実体への操作 | 動詞を追加 | `/dashboard/profile/edit` |

名詞だけの URL に編集画面を置かない。`/dashboard/profile` のように名詞で終わる URL は「閲覧」を期待させ、実体が編集ウィザードだと URL と中身が食い違う。

**作成と編集は URL を分けない。** 同一実体に対する同一の操作であり、初回か否かは状態の違いにすぎない。画面側で文言を出し分ける。

### 原則3: 詳細は一覧の下に置く

一覧が `/players` なら詳細は `/players/[accountId]` とする。

ルート直下に `/[accountId]` を置く形（GitHub / Zenn 型）は採らない。`/about` `/event` `/admin` `/dashboard` 等の既存パスと衝突し、**予約語リストの管理という恒久的な負債**を負うため。一覧配下なら衝突は原理的に起きない。

### 原則4: 認証境界を階層で表す

ログイン必須の画面は `/dashboard` 配下に集約する。URL を見れば認証が要るか判別でき、認証境界を **`src/middleware.ts` の `SESSION_REQUIRED_PATHS`（`/dashboard/*` `/onboarding/*`）1 箇所**で表せる。`page.tsx` は認証を判定しない（[`bff/design.md`](./bff/design.md)）。新しいログイン必須画面は `/dashboard` 配下に置くだけで保護される。

### 原則5: アカウント設定と公開物の編集を混ぜない

同じログイン後の画面でも、責務が異なるものを同階層に並べない。

| 対象                     | 性質                         | 置き場                    |
| ------------------------ | ---------------------------- | ------------------------- |
| email / accountId        | User 集約のアカウント設定    | `/dashboard/settings`     |
| アーティストプロフィール | 公開物（ArtistProfile 集約） | `/dashboard/profile/edit` |

`/dashboard` 直下は**ログイン後ホーム（概況と導線）**であり、設定項目を直接置く場所ではない。

### 原則6: BFF の read route は画面パスに一致させる

[`bff.md`](./bff/design.md) は「route はリソース名ではなく画面名で切る」と定める。beatfolio では**画面名 = 画面の URL パス**であるため、両者を機械的に対応させる。

```
画面  /dashboard/profile/edit
BFF   /api/dashboard/profile/edit
```

対応が1対1なら、画面を見れば呼ぶべき route が決まり、route を見れば供給先の画面が決まる。api-server のリソース構造（`/api/users/me` 等）を BFF の URL に写さない。
