# BFF のマルチクライアント展望（Web / iOS）

> **位置づけ**
> 本ドキュメントは [`bff.md`](./design.md) の延長として、**複数のクライアント（Web / iOS 等）を持つようになった場合に BFF がどう発展するか**を整理した将来展望である。
> 現時点で iOS 向け BFF を実装するものではない。**いま守るべきは「将来 standalone に抽出できるよう substrate を保つ」ことだけ**である（[`bff.md` の責務定義](./design.md) を前提とする）。

---

## 結論

> **BFF は論理的には独立したレイヤーである。現状 Client App に統合されているのは Next.js App Router の都合にすぎず、①マルチクライアント化、または ②Web の構造変更（SSR 喪失）を契機に、独立したサービスとして分離されうる。api-server は1つのまま共有される。**

これは例外ではなく **BFF パターン本来の姿**である。"Backend **For Frontend**" は元来「フロントエンドごとに1つ」を前提とした概念であり、[`bff.md`](./design.md) で定義した「特定の画面に必要なデータを返す／観点を緩和する」という責務を **クライアント単位までスケールさせた**ものに過ぎない。

---

## 現状: なぜ BFF が Client App に統合されているのか

Next.js App Router は2つの役割を1つのデプロイに同梱している。

- **UI 描画**（RSC / SSR）→ `page.tsx` が BFF read route を呼んで初期レンダリングする場所
- **サーバーランタイム**（Route Handlers `/api/*`）→ write の HTTP ルートが乗る場所

BFF はこの両方を間借りしている。つまり **BFF が同じ Client App に統合されているのは「埋め込む先（サーバーランタイム）がたまたまそこにあるから」というデプロイ/ランタイム上の都合**であって、アーキテクチャ上の必然ではない。論理的には BFF は最初から別レイヤーである（[`bff.md`](./design.md) でそう定義した）。

> 現状の統合は「現時点の最適解」であって、ロックインではない。
> BFF ロジックを Next.js 非依存に保っている限り、統合と分離は自由に選び直せる。

---

## 分離を駆動する2つの要因

埋め込み先（サーバーランタイム）が無くなる／クライアントが増える構造変更が起きると、BFF は standalone なサービスとして表に出る。駆動要因は2つある。

| #   | 駆動要因                                                                                                                 | 何が起きるか                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **マルチクライアント化**（Web / iOS …）                                                                                  | クライアントごとに画面・観点が違う → BFF が per-client に分かれる。iOS には埋め込む Next.js が無いため iOS BFF は standalone                                                                                            |
| ②   | **Web の構造変更（SSR 喪失）**（純粋 SPA / Vite、フロントとサーバーの分割、Hono standalone / TanStack Start 等への移行） | read の経路は変わらない（[`bff.md`](./design.md) で read も write も既に HTTP route 経由）。変わるのは**埋め込み先（Next.js ホスト）が無くなる**ことで、既に HTTP な BFF route が **standalone サービスとして表に出る** |

> **read も write も最初から HTTP route 経由**（[`bff.md`](./design.md) の対称設計）なので、Web は read の経路という点で**最初から iOS に近い形**になっている。
> ②で SSR を外しても read を HTTP 化し直す書き換えは要らない。route はそのまま、ホスト（Next.js）から切り離して別デプロイへ移すだけで standalone 化できる。

### 「表示側の技術スタックの差」が駆動するもの／しないもの

分離の根本にあるのは「**表示される側が異なる**」ことだが、その因果を正確に押さえる。**変わるのはクライアント側のスタックであって、BFF 自身の実装スタックとは限らない**。

| 表示側で変わるもの                                | BFF への影響                                                                                                                                  |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **画面・必要なデータ**（Web の画面 ≠ iOS の画面） | shaping（集約・整形・そぎ落とし）が per-client になる → BFF が分かれる（要因①の本質）                                                         |
| **ランタイム**（SSR の有無）                      | read route を**呼ぶ主体**が変わる。Web は SSR の `page.tsx`（自己 HTTP hop）、iOS は native（HTTP）。route 自体は両者とも HTTP（要因②と同根） |
| **クライアント言語**（Swift 等）                  | クライアント↔BFF の**プロトコル/契約**は変わるが、**BFF の実装言語は縛られない**                                                             |

- **BFF は依然サーバーサイドの層**である。iOS の BFF が Swift になるわけではなく、サーバーサイド（多くは TypeScript）のまま立つ。クライアントが Swift だからといって BFF まで Swift にはならない。
- 分離するのは **「クライアントごとの BFF インスタンス」**であって、**BFF の実装スタックがクライアント言語に追従するわけではない**。

#### このプロジェクト特有の補足: 共有境界は型安全のまま保つ

beatSinkCentral は **hono client（`hc<AppType>`）で api-server まで型を通す**ことに投資している。そのため iOS BFF を立てる場合でも、**BFF 側は TypeScript のまま**にして api-server への型付きクライアントを維持するのが自然。

```
クライアント ↔ BFF        … 表示側ごとに異なる（言語・プロトコル・shaping）
BFF ↔ api-server          … TypeScript + 型付き hono client のまま共有（分離後も型安全を維持）
```

→ 分離しても変わるのは「クライアント↔BFF」の側だけ。**「BFF↔api-server」の型安全な境界は、どのクライアント向けの BFF でも共通して保てる**。

---

以降、①の詳細（クライアントごとに分かれる理由）を述べる。

## なぜクライアントごとに BFF が分かれるのか

BFF の責務を「特定の画面に必要なデータを返す中間層」と定義した以上、**Web の画面 ≠ iOS の画面**である。必要なデータの形・そぎ落とし方・集約の仕方がクライアントごとに異なるため、整形を担う BFF も自然と分かれる。

```
Web (Next.js) ──▶ Web BFF  ─┐
                             ├──▶ api-server（共有・ドメイン単位）
iOS (native)  ──▶ iOS BFF  ─┘
```

- **api-server は1つ** — ドメイン／業務ロジックはクライアントに依存しない
- **BFF はクライアントごと** — 画面・観点が違うので、整形／そぎ落としも違う

> 1つの BFF で Web も iOS も賄おうとすると、観点の緩和が効かなくなり、BFF ではなく**汎用 API ゲートウェイ**に化ける（= BFF の anti-pattern）。クライアントごとに分けるのが正攻法。

---

## 「独立する」≠「api-server になる」

BFF が独立したサービスになっても、**役割の層は api-server とは別のまま**である。混同しないこと。

|                  | api-server                   | BFF（Web / iOS）               |
| ---------------- | ---------------------------- | ------------------------------ |
| 役割             | 共有のドメイン／業務ロジック | クライアント固有のプレゼン整形 |
| クライアント依存 | しない                       | する（per-frontend）           |
| 数               | 1つ                          | フロントエンドの数だけ         |

iOS の BFF が独立したサービスになるのは、**埋め込む先（Next.js のホスト）が無いから**であって、api-server と同じ責務になるからではない。iOS BFF は standalone なサービス（Hono standalone 等）として立つ、という形になる。

---

## 現在の設計への含意

この展望に照らすと、[`bff.md`](./design.md) の設計（read も write も HTTP route 経由で対称）は **そのままマルチクライアントへ素直に伸びる**。Web 固有なのは「誰が route を呼ぶか」だけである。

### 1. read/write の経路は Web も iOS も HTTP route で対称

`bff.md` で read も write も `/api/*` の HTTP route 経由に揃えた。iOS でも同じく HTTP route。**違いは「read route を呼ぶ主体」だけ**である。

|                  | Web                                  | iOS                         |
| ---------------- | ------------------------------------ | --------------------------- |
| read を呼ぶ主体  | SSR の `page.tsx`（自己 HTTP hop）   | native クライアント（HTTP） |
| write を呼ぶ主体 | ブラウザの hook                      | native クライアント（HTTP） |
| BFF route 自体   | `/api/*`（Hono app、Next.js に同梱） | standalone（Hono app）      |

→ route の形（Hono ハンドラ）は共通。クライアント側の呼び出し主体とデプロイ先だけが違う。

### 2. だから整形ロジックは BFF route（Hono app）に閉じる

整形／そぎ落としロジックを `page.tsx` にベタ書きせず、**BFF read route（Hono ハンドラ）**に置いておけば、将来 standalone BFF 化は **その Hono app をホスト（Next.js）から外して別デプロイに載せるだけ**で済む。Hono route は Next.js 非依存なので移植性が高い。

> **現コードとのズレ**: 現状の Web の read は `page.tsx` が api-server を直接叩いており（[`bff.md`](./design.md) の規範からズレ）、整形が route に集約されていない。`bff.md` の対称設計（read も BFF route 経由）への移行が、この移植性を満たす前提条件になる。

### 3. 共有境界は「api-server とその client SDK」まで

クライアント間で共有されるのは **api-server とその呼び出し用 client SDK（hono client + 型）**まで。整形ロジック（BFF route）は per-client であり、Web の route を iOS が再利用するとは限らない。**共有の線は api-server クライアントの層に引く**。

```
共有 ────────────────┐
  api-server          │  ← ドメイン
  api-server client   │  ← hono client + 型
────────────────────┘
per-client ──────────┐
  Web BFF route       │  ← 画面整形（Web）
  iOS BFF route       │  ← 画面整形（iOS）
────────────────────┘
```

---

## いま守ること（substrate）

- iOS BFF も、Web BFF の standalone 化も、**まだやらない**。
- 守るのは2点: **(1) read を `page.tsx` 直呼びではなく BFF read route 経由にする**（[`bff.md`](./design.md) の対称設計）。**(2) BFF route の整形ロジックを Next.js 非依存の Hono app に保つ**（Next 固有 API に依存させない）。これにより、①マルチクライアント化または②構造変更が現実になった時、standalone BFF への抽出が **「Hono app をホストから外して別デプロイに移すだけ」**（書き直しではない）で済む。
- 設計（substrate）で分離に備え、scaffolding（実際の standalone BFF）は必要になるまで作らない。
