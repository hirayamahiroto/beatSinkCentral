# テスト戦略 整備プラン

本ドキュメントは、テスト設計・実装・レビューをチーム共通の指針に乗せるための整備計画（フェーズの定義と進捗）。規範本体は [`strategy.md`](./strategy.md)。

---

## 背景

整備前は、テストに関するドキュメントが「実行コマンド」までで、**テスト設計（何を・どの粒度で・どのレイヤーでテストするか）の方針** が文書化されていなかった。Phase 1 で `strategy.md` に次を定めた。

- テスト戦略（テストピラミッド、各レイヤーで何をテストするかの基準）
- カバレッジ方針
- モック方針（DB・外部 API・時間・乱数の扱い、依存先の型で縛る規則）
- レビュー時のテスト要件（code-review-checklist §15）

## 目的

テスト設計の判断・実装・レビューが、属人的・場当たり的にならず、**チーム共通の指針** に沿って行えるようにする。

---

## 整備フェーズ

本整備は一度に全てをやらず、**優先度に沿って段階的に積み上げる**。下記フェーズ順に進め、前フェーズが固まる前に次に進まない。

### Phase 1（現在）: Unit Test の整備

- 対象: Value Object / Entity / Policy / Usecase / Repository / Entrypoint の単体テスト（Sociable Unit Test 含む）
- 成果物: [`strategy.md`](./strategy.md) / code-review-checklist §15 / CLAUDE.md からの導線（レイヤー別ガイドラインとテストケーステンプレートは別冊にせず `strategy.md` §12 とチェックリストに吸収した）
- 理由: **最小単位から組み上げる実装方針の土台**。Unit が甘い状態で上位を積んでも意味を成さない
- 本プロジェクトのテスト戦略の **主軸** がここ

### Phase 2（後続）: Integration Test の整備

- 対象: Repository を実 PostgreSQL に対して検証する統合テスト
- 必要になるもの: Docker Compose の DB / Transaction rollback / fixture 機構 / CI 統合
- 理由: Drizzle クエリと実スキーマの整合、マイグレーション適用後の動作など、単体では検証不能な領域をカバー
- **Phase 1 が固まり、実装が増えて実 DB 乖離のリスクが具体化してから着手**

### Phase 3（必要なら）: E2E Test の整備

- 対象: クリティカルパス（例: 認証→登録→取得）の HTTP → 実 DB 一気通貫
- 理由: 原則として **Phase 1（Entrypoint 単体テスト）+ Phase 2（Repository 統合）で代替可能** なため必須ではない
- ただし本番デプロイ後のスモークテストは別途検討
- 設計候補は [`e2e-strategy.md`](./e2e-strategy.md) に記録済み（今は読まなくていい）

方針の背景（古典派を採る理由、隔離の基準を純粋性に置く理由、定番の批判への回答）は `background.md` に記す。

### フェーズ跨ぎの判断基準

| 次フェーズへ進む条件                       | 指標                                        |
| ------------------------------------------ | ------------------------------------------- |
| Phase 1 → Phase 2                          | Unit Test のレビュー観点がチームで定着し、新規 PR で自然に守られている |
| Phase 2 → Phase 3                          | 実 DB 統合の恩恵が出てもなお拾えない不具合が発生・予見される |

## `strategy.md` の目次

```text
0. 本プロジェクトにおけるテスト分類と優先度
1. テストの目的
2. 前提条件: 疎結合な設計
3. 積み上げ型テスト(Atomic Design 類推)
4. レイヤーごとのテスト責務
5. モック方針（契約をモックする / 依存先のインターフェース型を参照する）
6. カバレッジ方針（数値目標は設けない）
7. Integration Test / E2E Test の方針
8. エラーハンドリングのテストパターン
9. 時間・乱数・環境変数
10. テスト命名・配置規約
11. テストをいつ書くか
12. アンチパターン
```

## 決定事項

| 論点                                     | 決定                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------- |
| カバレッジ数値目標                       | 設けない（`strategy.md` §6）                                          |
| E2E の導入フェーズ                       | Phase 3。原則整備しない（`strategy.md` §7-4）                         |

| モックの書き方                           | 依存先のインターフェース型に `satisfies` で縛る（`strategy.md` §5）   |
