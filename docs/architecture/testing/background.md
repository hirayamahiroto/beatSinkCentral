# テスト設計の背景 — なぜ古典派を採り、隔離の基準を純粋性に置くのか

本ドキュメントは `strategy.md` の方針が **どの流派に立ち、なぜそれを選び、定番の批判にどう答えるか** を記録する。方針そのものは `strategy.md`、E2E の扱いは `e2e-strategy.md` を参照。ここは判断の根拠だけを書く。

新しいメンバーがルートテストで usecase が実物で呼ばれているのを見て「これは単体テストではないのでは」と感じたとき、あるいはレビューで「usecase もモックすべきでは」と言われたときに、毎回説明せずに済むようにするための文書である。

---

## 1. 結論

本プロジェクトのテスト戦略は **古典派（Classical school）** に立つ。ただし古典派の隔離基準「実物が使いにくいものだけ差し替える」を、**「不純なものだけ差し替える」** に機械化している。

```text
差し替えない（実物を呼ぶ）              差し替える（モックする）
──────────────────────────────         ──────────────────────────────
純粋な核                                不純な殻
  Value Object                            Repository（DB）
  Entity / Aggregate                      外部 API クライアント（Auth0、Storage）
  Policy / Domain Service                 時刻（Date / Clock）
  Usecase                                 乱数（ID 採番は factory 内に閉じ、テストでスタブ）
                                          環境変数
判定基準: 同じ入力に同じ出力を返し、外界に触れないか
```

ルートテストで usecase が実物で呼ばれ、Repository だけがモックされているのは、この基準の結果である。

---

## 2. 二つの流派

| 観点           | 古典派（Classical / Detroit）                    | ロンドン派（Mockist / London）                         |
| -------------- | ------------------------------------------------ | ------------------------------------------------------ |
| 隔離の単位     | テスト同士（状態を共有しない）                   | テスト対象のクラス／関数（協力者はすべて差し替える）   |
| 差し替える対象 | 実物が使いにくいもの（DB、ネットワーク、時刻）   | テスト対象以外のすべての協力者                         |
| 検証するもの   | 出力と状態（入出力が正しいか）                   | 協力者との相互作用（どう呼んだか）                     |
| リファクタ耐性 | 高い。入出力が同じなら内部を組み替えても落ちない | 低い。協力者の呼び方を変えると落ちる                   |
| 構造的な弱点   | 下層の壊れが上層に連鎖する                       | モックが実装と乖離しても単体では検知できない（偽パス） |
| テストの主目的 | 振る舞いの固定と回帰の検知                       | 設計のフィードバック（モックは設計の道具）             |

両派とも **プロセス外の依存（DB、HTTP）は差し替える** 点は一致している。また Freeman & Pryce 自身が「値オブジェクトはモックしない」と明記しており、対立点は **振る舞いを持つプロセス内の協力者**（usecase、domain service、repository の呼び出し側）をモックするか否かに絞られる。

後続の整理として Khorikov『Unit Testing Principles, Practices, and Patterns』(2020) は、モックしてよいのは「管理していないプロセス外依存」だけで、自前の DB は統合テストで実物に対して検証すべきだとする。本プロジェクトの §7-3（Repository の Integration Test を必ず書く）はこの整理に沿う。

## 3. なぜ古典派か

### 3-1. 検知したいのは振る舞いの回帰だから

本プロジェクトのテストは「実行可能な仕様」であり（`strategy.md` §1）、守りたいのは **入力に対して何が返るか** である。協力者をどう呼んだかは仕様ではなく実装の都合で、そこを固定すると内部を組み替えるたびにテストが落ち、リファクタの摩擦がテストを書く動機を削る。

ロンドン派がモックから得る「設計のフィードバック」は、本プロジェクトでは層の構造（VO → Entity → Policy → Usecase → Entrypoint）と依存の向き（`../server/architecture.md`）を先に決めることで得ている。モックで協力者のインターフェースを発見する必要がないため、ロンドン派の利点を取り込む余地は小さく、弱点（偽パス、リファクタ耐性の低さ）だけが残る。したがって古典派を採る。

### 3-2. 偽パスを構造的に消したいから

この方針に至った直接の契機は、層ごとに独立したモックを置いていた時期に、別の層の変更がモックに反映されず、**モックが古い契約のまま固定値を返し続けてテストは緑、壊れているのは本番だけ** という状態を経験したことである。

層ごとに独立したモックは、他の層の変更から自分を切り離す。それはテストを安定させると同時に、検知範囲を狭める。デグレを検知するために書いたテストが、モックの独立性ゆえにデグレを見逃していた。

対策は「モックを人が同期し続ける」ことではなく、**同期そのものを不要にするか、同期漏れをコンパイルエラーにする** ことである。

| 偽パスの発生源                         | 何が起きるか                                                    | 対策                                                                              |
| -------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 純粋関数をモックする                   | 実装が壊れてもモックは固定値を返し続ける                        | モックしない。実物を呼ぶ（同期が不要になる）                                      |
| モックが型を参照していない             | 依存先の型が変わってもモックは古い形のまま通る                  | `vi.fn<I["method"]>()` + `satisfies I` で縛る（同期漏れがコンパイルエラーになる） |
| フィクスチャを手書きする               | 依存先の値の意味が変わってもフィクスチャは古い意味のまま        | factory で生成する（依存先が自分で更新する）                                      |
| 殻のモックと実装の一致を誰も確かめない | モックした契約と実際の DB・API の契約がずれても単体では検知不能 | 殻に契約テストを置き、CI で実インフラに対して流す（Phase 2）                      |

いずれも「人の注意」を「機械の強制」に置き換えている。この方針は考える量を増やす設計ではなく、減らす設計である。

## 4. 隔離の基準を「純粋性」に置く理由

古典派の隔離基準「実物が使いにくいものだけ差し替える」は、何が「使いにくい」かの判断を人に委ねる。本プロジェクトはこれを **「不純なものだけ差し替える」** に置き換える。純粋か不純かは、その関数が外界（DB、ネットワーク、時刻、環境変数）に触れるかどうかで機械的に決まるため、レビューで「これはモックすべきか」を議論する余地がない。

**前提**: この基準が機能するには、核が本当に純粋でなければならない。domain や usecase の中に `new Date()` や `crypto.randomUUID()` や DB 呼び出しが紛れ込むと、「実物を呼ぶ」が「副作用を呼ぶ」になり、古典派の定番の弱点（遅い、非決定的）がそのまま現れる。時刻は境界で取得し、核は引数で受け取る（`strategy.md` §9 参照）。

ID 採番だけは例外として factory に閉じる。ID は Entity の同一性そのもので、外から渡すと呼び出し側が採番責務を負ってしまうため、生成器を注入しない（`../server/architecture.md`「Factory」）。`crypto.randomUUID()` は I/O ではなく、この定義の「純粋」を破らない。決定性が必要なテストでは `crypto.randomUUID` をスタブする。

## 5. 古典派への定番の批判と、本プロジェクトでの回答

### 「実物を呼ぶと遅い」

この批判が出た 2000 年代の文脈では、「協力者を実物で呼ぶ」が「DB やファイルシステムまで実物で呼ぶ」を意味していた。純粋と不純を分ける規律がないコードベースでは、実物の協力者の先に I/O があるのが普通で、だから遅かった。

純粋な核が分離されていれば、実物の協力者を呼ぶコストは関数呼び出しのコストである。本プロジェクトの api-server の全ユニットテスト（約 700 件）は数秒で終わる。遅いとすれば核に不純物が混じっているサインであり、テストを速くするためにモックを増やすのではなく、不純物を境界へ追い出す（§4 の前提）。

### 「下層が壊れると上層のテストが連鎖して落ち、原因が特定しにくい」

連鎖して落ちること自体は欠陥ではなく、下層の変更が上層の振る舞いを変えたという **正しい検知** である。原因の特定は、積み上げ型の構造（`strategy.md` §3）で下層から順に見れば済む。VO のテストが落ちていればそこが原因で、上層の失敗はその結果にすぎない。

ロンドン派ならこの場面で上層のテストは緑のまま保たれるが、それは上層が下層の壊れを **見逃している** だけである。§3-2 で経験した偽パスはまさにこの形だった。

### 「usecase を実物で呼ぶルートテストは単体テストではない」

「単体」を関数やクラスの単位で取ればそのとおりで、これは Sociable Unit Test（`strategy.md` §0）である。本プロジェクトは「単体」を関数ではなく **振る舞いの単位** で取る。ルートテストの単位は「この HTTP リクエストに対して何が返るか」であり、その振る舞いを実現するために usecase や Entity が内側で動いているのは実装の詳細である。

## 6. ロンドン派から借りているもの

以下はロンドン派の道具だが、古典派が DB や外部 API に対して使うものと同じであり、思想としてロンドン派を採用しているわけではない。

- 殻の境界にモックを置く
- 境界での呼び出しを `toHaveBeenCalledWith` / `not.toHaveBeenCalled` で検証する。ただし **観測可能な副作用**（DB にどの値で問い合わせたか、問い合わせに到達しなかったか）に限り、「協力者をどう呼んだか」の検証には使わない
- モックを型に縛る。これは流派ではなく TypeScript の実装手段

outside-in（モックで協力者のインターフェースを発見しながら外から作る）は採用しない。本プロジェクトは VO → Entity → Policy → Usecase → Entrypoint の順に内から外へ組み上げる（`strategy.md` §11）。
