# DB 設計思想（マスタ参照モデル）

> **このドキュメントの位置づけ**
>
> 種別・媒体・分類など「**固有の語彙を持つデータ**」をどうモデリングするかの設計思想を定義する。
> スキーマ変更・新テーブル追加時の判断基準として参照する。
> マイグレーションの手順は [`database-migration.md`](./migration.md)、接続は [`database-connection.md`](./connection.md)、全体レイヤー構成は [`architecture.md`](../architecture.md) を参照。
> 汎用的なクエリ品質（N+1・スコープ条件・過剰取得等）は [`.claude/rules/code-review-checklist.md`](../../../../.claude/rules/code-review-checklist.md)。

---

## 1. 原則: データを「定義層」と「利用層」の二層に分ける

データを次の二層に分けて設計する。**固有の値（種別名・媒体名など）を利用層に直接書かず、定義層を参照する**。

```
[定義層 / マスタ]  どんな種別・媒体が世界に存在するか（全主体で共有される語彙）
      ▲ 参照（FK）
[利用層 / 参照]    ある主体が、その種別を、どんな値で使っているか（主体ごとの実体）
```

- **定義層（マスタ）** — 種別・媒体・分類の「語彙そのもの」を一元管理する。
- **利用層（参照）** — 語彙を使った業務インスタンス。マスタを **FK で指すだけ**にし、値を複製しない。

> enum 文字列やフリーテキストで種別を各行に散らさない。語彙は一箇所（マスタ）に集約し、実体はそこを参照する。

---

## 2. 設計の手順（問いの順序）

種別を持つ構造（SNS / リンク・ステータス・分類など）を設計するときは、必ずこの順で問う。

1. **何を管理するか（定義層を先に決める）** — 「どんな媒体／種別が存在するか」。これがマスタになる。
2. **それがどう繋がるか（利用層を次に決める）** — 「ある主体に、どの種別の、どんな値が紐づくか」。これがマスタを参照する実体になる。

> 例（リンク）: ①まず「どの媒体を管理するか（YouTube / X / …）」を定義 → ②次に「あるプロフィールに、どの媒体の、どの URL が繋がっているか」を定義する。

---

## 3. 各層の性質

| 観点     | 定義層（マスタ）                                                   | 利用層（参照）                                                                   |
| -------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 表すもの | 種別・媒体・分類の **語彙そのもの**                                | 語彙を使った **業務インスタンス**                                                |
| 変更頻度 | 有限・低頻度（語彙は滅多に増減しない）                             | 主体の操作で随時増減する                                                         |
| キー     | 不変の機械コード（`code`, `unique`）＋ 表示名                      | サロゲート PK ＋ 対象への FK ＋ **マスタへの FK**                                |
| 付帯情報 | 語彙固有の属性（label / icon / 説明 など、その種別に内在するもの） | 監査列（created / updated / deleted・変更者）／有効性制約（必要なら部分 unique） |
| 論理削除 | 基本不要（参照データ）                                             | 基本必要                                                                         |

> **マスタは語彙の定義に徹する。「どう並べる・どう出し分けるか」は持たせない。**
> 表示順・出し分けなど「どう使うか」は UI 側（または利用層のデータ）が決める。
> マスタが持つのは種別に**内在する属性**（不変コード・正式名称・アイコン等）だけで、`sort_order` のような**利用側の都合**を定義層に入れない。
> 利用層は、その主体が選んだ並び順など「使い方」を持ってよい（例: あるプロフィールが自分のリンクを並べた順）。

---

## 4. マスタ化する / しないの判断基準

「**基本はマスタで管理する**」を既定にしつつ、線引きを明示する。

### マスタにする

次のいずれかに当てはまるもの（種別・媒体・分類・意味を持つステータス）。

- 語彙が有限で意味を持つ
- 語彙固有の属性（ラベル・アイコン等、種別に内在するもの）を伴う
- 将来増えうる（データで追加したい）
- **種別単位で集計したい**（例: 外部遷移の媒体別計測）
- 参照整合性が欲しい

### あえてマスタにしない（例外・理由を明示する）

- まだ語彙が定まらず、**自由入力で観察する段階**のもの。
  - 例: `genres` は現状あえて `varchar` 直持ち（インライン）。
  - 根拠: [`profile-information-design.md`](../../../product/profile-information-design.md) 「当面は自由入力。語彙が見えてから固定化」と整合。
  - 語彙が安定したらマスタへ昇格する、が既定路線。

> 同じ親（プロフィール）配下でも判断は分かれる。**`links` ＝ マスタ参照／`genres` ＝ 当面インライン**。
> 判断軸は「語彙が確定して、表示・計測の対象になるか」。

## 5. 規範例（既存実装）

このモデルはコードベースに既に存在する規約であり、新規発明ではない。

- **定義層**: `artist_status_masters`（`status_code` unique ＋ `status_name` ＋ `description`、`serial` PK、タイムスタンプ無し）
- **利用層**: `artist_statuses`（`uuid` PK、`artist_id` FK、`artist_status_master_id` FK、`changed_by_user_id`、論理削除、active な部分 unique index）

新しく種別を持つ構造を作るときは、この二層を範とする。

---

## 6. 適用例: プロフィールのリンク（媒体マスタ参照）

> 背景: 現状の `artist_profile_sns_links` は `url` のみを持ち種別を保存していない。種別はウィザード UI でしか存在せず、読み戻し時に URL から推定しており脆い（"その他" は判別不能）。本モデルで「種別を保存して参照する」形に直す。

- **定義層（媒体マスタ）** — 世界に存在する送り先の種類（YouTube / X / Instagram / TikTok / …）。`code`・正式名称・アイコンなど**媒体に内在する属性**を持ち、データで増やせる。並び順や出し分けといった「どう使うか」は持たない（UI 側の判断）。
- **利用層（プロフィール ↔ リンク）** — あるプロフィールに、どの媒体の、どの URL が繋がっているか。媒体マスタへの FK ＋ URL ＋（媒体が "その他" 等のとき）任意ラベル ＋ **そのプロフィール自身が選んだ並び順**（利用側のデータ）。

これにより:

- 「何のリンクか」は **保存された参照から確定**する（URL からの推定が不要になる）。
- 媒体単位の外部遷移計測が、参照整合性つきで可能になる（[`profile-information-design.md`](../../../product/profile-information-design.md) §5-2 のファネル計測と整合）。

> 具体的なテーブル定義・ドメイン／API／BFF への影響は、本思想に沿って別途スキーマ設計で確定する。

## 7. UI への波及（表示情報の出所と加工責務）

マスタ参照モデルは UI まで一貫させる。**画面に出す情報は、基本すべて DB を出所とする**。フロントにドメイン語彙（種別ラベル・アイコン・選択肢など）をハードコードしない。

### 7-1. 責務の連鎖

```
DB（マスタ＋利用層）
   │  正しい単位で返す
api-server（汎用 API）        ドメインとして正しい汎用エンドポイント。画面都合を持たない
   │  画面に必要な形へ加工
BFF（/api/*）                 集約・整形・そぎ落とし／マスタ参照の解決（code → label / icon）
   │  解決済みの表示用データを props で渡す
UI（packages/ui）            受け取った形を描画するだけ。取得もドメイン語彙の保持もしない
```

| レイヤー       | 責務                                                                   | やらないこと                                     |
| -------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| **api-server** | ドメインとして正しい **汎用 API**（マスタ一覧・詳細など）を提供        | 画面都合の整形                                   |
| **BFF**        | 汎用 API を画面が必要な形へ **加工**。**表示用の加工制御はここに集約** | ドメイン判断                                     |
| **UI**         | 受け取った表示用データを **描画**                                      | データ取得・ドメイン語彙のハードコード・値の変換 |

> 詳細な read/write の厚みと経路は [`../../frontend/bff/design.md`](../../frontend/bff/design.md)（read 厚い・write 薄い）に従う。本節はそこへ「**表示語彙も DB 由来**」という出所の制約を加える。

### 7-2. マスタ語彙の供給経路

マスタ（`link_type` 等）は次の経路で UI に届く。**DB でマスタを足せば、UI の選択肢・表示も自動で揃う**。

```
link_type マスタ ──▶ api-server 汎用API（種別一覧）──▶ BFF（画面用に整形）──▶ page/ClientAdapter ──props──▶ UI 組織
```

- 選択肢（ウィザードのドロップダウン等）も DB マスタ由来にする。フロントに固定リストを持たない。
- `packages/ui` は Next 非依存・データ取得をしないため、マスタ取得は **app 層（page / ClientAdapter）** が行い、組織コンポーネントへ **props で渡す**（[`../../frontend/ui/component-design.md`](../../frontend/ui/component-design.md) のレイヤー責務に準拠）。

### 7-3. 値の解決は BFF（UI で code をラベルに変換しない）

- 利用層が持つのは **code / FK**。表示に必要な **label / icon への解決**（join やマッピング）は **BFF が行い**、UI には解決済みの形で渡す。
- UI に code だけ渡してフロントでラベル変換するのは、**語彙のハードコード**であり禁止（§7-1）。

### 7-4. 適用上の境界（過剰適用を避ける）

- 「DB 由来」の対象は **ドメイン語彙・業務データ**（種別・名称・本文・選択肢など）。
- 純粋な UI コピー（ボタン文言「次へ」、見出しの定型文など、ドメインに属さない表示文字列）は UI に置いてよい。
- 判断軸は §4 と同じ：「それは管理すべき語彙か、単なる画面の飾りか」。

### 7-5. 現状のアンチパターン（是正対象）

- ウィザードが媒体の選択肢（`PLATFORM_OPTIONS`）と活動形態ラベルを **フロントにハードコード**している。
- リンク種別を保存せず、読み戻し時に **URL から推定**している（フロントでの値変換＝§7-3 違反）。

→ 本モデルでは、媒体は `link_type` マスタ由来・BFF で解決し、UI は受け取って描画するだけにする。
