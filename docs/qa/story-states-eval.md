# story-states 評価設計 — 指標と手戻り評価

story-states パイプライン（①map → ②gen → ③run → ④triage）が **狙った価値を達成しているか** を、パイプライン自身の成果物から継続的に測るための設計。指標のための新しい計測基盤は作らない。**情報モデル（評価台帳＋指標定義）が substrate、集計は薄い**。

関連スキル: `.claude/skills/story-states-{map,gen,run,triage}`。

## 1. 何を「達成」とみなすか（価値定義）

`triage` スキルの言葉がそのまま価値定義：

> 緑は価値ではなく、赤を安く調査可能にすることが価値。

したがって測るのは緑の数でもカバレッジ率でもない。この2つは vanity metric：

- **カバレッジ率** … `render only`（play 無しスモーク）でいくらでも水増しできる。
- **緑の件数** … 何もアサートしない緑は無価値。

測る価値は2軸：

- **赤の信号品質** … 出た赤が本物か（信用に足るか）。
- **手戻りの前倒し/削減** … 本来もっと高コストな段階で起きる手戻りを、安い段階に引き寄せられているか。

## 2. 「手戻り」を3つに割る（評価の肝）

「継続的な手戻りがあったか」を一括で悪と測ると評価を誤る。triage の2分類がそのまま手戻りの性質分けになる：

| 種別              | 正体                                                             | 良し悪し                                                          | 目標               |
| ----------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------ |
| **良い手戻り**    | real-bug 由来。本番/レビュー前に本物のバグを捕まえて実装を直した | ✅ これが粗利。無ければ後工程で高コストに起きていた手戻りの前借り | 捕捉数を可視化     |
| **悪い手戻り**    | test-drift 由来。実装は正しいのに期待値/fixture を直す保守作業   | ❌ 自動化の負債                                                   | 時系列で**下降**   |
| **churn（再発）** | 同一 state が 赤→直す→また赤 を繰り返す                          | ❌ 不安定・設計の匂い                                             | 発生ゼロに近づける |

## 3. 評価台帳（single source）

指標の素は 1 本の append-only 台帳 `docs/qa/story-states-ledger.md`。③run が実行ごと、④triage が仕分けごとに 1 行追記する。Markdown テーブルにして人間の可読性と git diff を両立させ、集計は行をパースする薄いスクリプト（または月次手動）で行う。

列（③run §4 / ④triage の出力と一致させる）：

| 列           | 値                                                         | 誰が書く            |
| ------------ | ---------------------------------------------------------- | ------------------- |
| `date`       | YYYY-MM-DD                                                 | run                 |
| `branch`     | ブランチ名                                                 | run                 |
| `target`     | カタログの target-slug                                     | run                 |
| `stateKey`   | `<Component>:<storyName>`（安定キー）                      | run                 |
| `gen`        | `play` \| `smoke` \| `none`                                | run（②gen の結果）  |
| `run`        | `pass` \| `fail`                                           | run                 |
| `triage`     | `real-bug` \| `test-drift` \| `要確認` \| `-`（passは`-`） | triage              |
| `provenance` | `spec` \| `impl`（markerの出所。impl=①mapの※仕様確認）     | run（カタログ由来） |
| `escape`     | `yes` \| `-`（§7 参照）                                    | 人 / triage         |

`stateKey` を安定キーにすることで、churn・drift・precision がすべて台帳の集計だけで出る。

## 4. 指標定義（6 + 1）

ウィンドウ（例：直近1ヶ月 / 直近ブランチ群）で台帳を集計する。

| 指標               | 式                                                         | 目標方向                   | 意味                                                                     |
| ------------------ | ---------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------ |
| **Red精度**        | `real-bug / (real-bug + test-drift)`                       | 高いほど良い               | 赤の信号品質。低いと「赤が信用されない」＝ triage が警告する状態そのもの |
| **Drift率**        | `test-drift / (run=fail 件数)`                             | **下降**                   | テスト保守負債（悪い手戻り）                                             |
| **循環率**         | `provenance=impl の状態数 / 全状態数`                      | **下降**                   | オラクル独立性。impl 由来はスモーク止まりで real-bug 判定に使えない      |
| **有効カバレッジ** | `gen=play の distinct stateKey / 検証対象 leaf の状態数`   | 上昇                       | スモークを除いた実質カバー。カバレッジ率の代わりに見る                   |
| **前倒し捕捉数**   | ウィンドウ内の `real-bug` 件数                             | 可視化（多い＝拾えている） | パイプラインの粗利＝良い手戻り                                           |
| **churn**          | `run=fail` を 2 つ以上の異なる `date` で持つ `stateKey` 数 | ゼロへ                     | 再発・不安定                                                             |
| **Escape**（+1）   | ウィンドウ内の `escape=yes` 件数                           | **下降**                   | §7。最重要の長期シグナル                                                 |

## 5. 集計と運用（薄く保つ）

- ダッシュボードは作らない。台帳テーブルの行を読む 20 行程度のスクリプト（`packages` 追加不要・Node/awk で可）か、月次の手動 rollup で §4 を算出する。
- rollup 結果は `docs/qa/reports/_summary-<期間>.md` に残す（推移が資産になる）。
- 指標のための実行時レイヤーは足さない。台帳という 1 ファイルが substrate。

## 6. 前提セットアップ（現状は未導入・正直に扱う）

このパイプラインは Storybook（`packages/ui` のみ）ベース。以下は**未導入**で、揃うまで③run はスモーク（例外なく render される）までを gate とする。無いものを緑扱いしない。

- **play の hard gate 化**：`@storybook/addon-vitest` ＋ Storybook v10 の test API。導入後、②gen の play が gate になる。正確な package/import は導入時に Storybook v10 のドキュメント（Context7 で確認）に従う。
- **フロー/E2E**：Playwright は未整備（複数画面フローは将来スコープ）。

導入の順は「まず render スモーク gate を安定させ、次に addon-vitest で play を gate 化、フローは最後」。段階ごとに §4 の有効カバレッジと Red精度で効果を確認する。

## 7. Escape ループ（複利）

§4 の 6 指標は「拾えた中の質」しか測れない。本当の「期待値達成」は**拾えなかったもの**でわかる：

- **Escape** = レビュー / 本番で見つかったバグのうち、**対応する catalog 状態が存在しなかった**もの＝①map の穴。

Escape が出たら、その状態を①map の catalog に積み（`escape=yes` で台帳にも記録）、②gen で story 化する。triage スキルの「bug由来の新規基準はカタログに積む＝複利」がこれで、**Escape が時系列で下がる ＝ 現実のバグ分布をカバーできてきている**。これがパイプラインが狙った価値を達成しているかの最終シグナル。

## 8. やらないこと

- カバレッジ率・緑の件数を成果指標にしない（vanity）。
- 手戻りを一括で悪と測らない（real-bug は前倒しできた良い手戻り）。
- 未導入の gate 基盤を「有る」ものとして緑扱いしない（③run はスモーク到達を正直に報告）。
- 指標のために新しい実行時レイヤー/ダッシュボードを作らない（台帳＋薄い集計）。
