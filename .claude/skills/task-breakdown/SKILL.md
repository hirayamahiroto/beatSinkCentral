# 要件 → 実装タスク分解ハーネス

## このスキルの目的

**「要件から直接コードに飛んでしまう」「タスクの切り方を毎回その場で考え直す」ことを防ぐ。**

要件と実装の間には、飛ばすと必ず手戻りになる中間成果物が 4 つある（画面契約・計測設計・インターフェース対応表・粒度の決まったタスク群）。このスキルは、その 4 つを**どの順で・どの完成条件で**作るかを固定する。

| このスキルがやること                       | やらないこと                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 分解の順序と各段階の完了条件を決める       | 設計規範そのものを定める（規範は `docs/`）                                                    |
| 各段階で参照する docs / skill を指す       | 実装手順を持つ（実装は `beta-ticket` 型のレール＋ `api-server-feature` / `frontend-feature`） |
| 止まってユーザーに確認すべき地点を明示する | 規範の無い判断を勝手に決める                                                                  |

> 実例（このハーネスの元になった適用）: `docs/plans/know-to-support-beta/plan.md` と統合 Issue #270。迷ったらこの実例の形に合わせる。

## 使うタイミング

新しい施策・機能群（複数チケットになる規模）の実装計画を立てるとき。単発の小改修には使わない。

---

## Step 0: 要件の完成度を確認する（入力ゲート)

分解を始める前に、要件側が次を満たすか確認する。満たさなければ**分解せず**、要件（discussions の PRD 等）を先に整える方向で相談する。

- [ ] 何を検証・達成するかが 1 文で言える（北極星・成功の定義）
- [ ] **不成立・失敗の定義**が書かれている（反証可能）
- [ ] **作らないもの（非対象）**が明記されている
- [ ] 期限・外部制約（ベータ週割り等）が分かる

## Step 1: 画面設計 — UI 契約を凍結する

要件を画面（区画・状態・操作）に落とし、**props 型＝契約**として凍結する。

- モックは Storybook に作る（`frontend-feature` skill・`docs/architecture/frontend/` に従う）。状態バリエーション（データあり/なし/最小）を story で網羅する
- **完了条件**: 契約が**表現非依存**であること — 見た目のパターンを差し替えても同じ props 型が成立する（複数パターンに同じ型を食わせて確認するのが確実）
- 語彙（ラベル・選択肢）は解決済みの形で受ける前提の型にする（`docs/architecture/server/database/design.md` §表示語彙）
- ここで凍結した props が、以降すべての段階の起点になる

## Step 2: ログ・計測設計 — 動線点にイベントを対応付ける

画面の各動線点（表示・展開・クリック・送信）に「**何の仮説・判断のためのイベントか**」を対応付けた表を作る。

| イベント | 発火点 | props | 対応する問い（仮説 ID・判断） |
| -------- | ------ | ----- | ----------------------------- |

- **意図 → イベントの順**で設計する。数値から入らない（計測の目的化を避ける）
- 原則: 発火は UI 層のみ・取り込みはエントリ層・PII を載せない（`docs/discussions/prd/know-to-support-verification/measurement-infrastructure-design.md` の原則を参照）
- **完了条件**: 要件側の各仮説・判断に、少なくとも 1 つのイベント（またはアナログ計測手段）が対応している。対応しない仮説が残るなら要件側に戻す

## Step 3: インターフェース設計 — 画面 → BFF → API の対応表

Step 1 の契約を「どう届けるか」を 1 枚の対応表にする。

| 画面・区画（UI 契約） | BFF ルート（read/write） | api-server エンドポイント | 担当チケット |
| --------------------- | ------------------------ | ------------------------- | ------------ |

- 規範: `docs/architecture/server/api-design-guidelines.md`（GET/POST のみ・リソースアドレッシング・1 ユニット 1 エンドポイント）と `docs/architecture/frontend/bff/design.md`（read は画面単位で厚く・write は薄く・語彙解決は BFF）
- read は「区画ごとに叩くか・集約 1 本か」をここで決める（N+1・過剰取得のレビューは実装後でなく**この表の上で**行う）
- 認証境界（公開 read / 本人 write / 認証不要の取り込み）を列挙し、公開範囲を明示する
- **完了条件**: ユーザーがこの表をレビューして凍結した状態。並行実装（レーン分割）はこの凍結が前提

## Step 4: タスク分解 — 粒度 3 層モデル

| 層            | 単位                                                                                 | 粒度の定義                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| **Issue**     | 要件への**約束 1 つ**（縦切り）                                                      | 約束が 1 文で言える。レイヤー横切り Issue（「API 全部」）は禁止                                               |
| **PR**        | **1 画面（または 1 区画）＋それを成立させる API・BFF・スキーマ一式**（縦切りが既定） | マージするとその画面・挙動が end-to-end で動く。1 セッションで完結・gate 全緑・マージ後に壊れた状態を残さない |
| **checklist** | 実装手順                                                                             | PR 内のステップ。Issue にしない                                                                               |

迷ったときの判定 4 つ:

1. 受け入れ条件が**観察可能な述語**か（「〜を確認する」は禁止。「X すると Y が記録される」の形に降ろす）
2. 1 PR ＝ 1 セッションで完結するか。しないなら割る
3. マージ後に中途半端を残さないか（未配線は可、動かない UI は不可)
4. 依存が一方向か

- **PR の既定は縦切り（画面＋API 込み）**。判定 2 に収まらない大きさになったときだけ、レイヤー境界で分割する（例: ①スキーマ＋ドメイン → ②API＋BFF → ③UI 配線）。分割する場合は**分解時に** Issue へ書いておき、途中 PR は「未配線だが緑」を保つ
- 各 Issue の本文は次の「タスク設計書フォーマット」に従う

### タスク設計書フォーマット（Issue 本文の型）

タスクは「何をするか」だけでなく、**要件との紐づけと最終挙動**を必ず持つ。この 3 点が書けないタスクは分解が間違っている。

```markdown
# <ID>: <タイトル（約束を 1 文で）>

## 紐づく要件

- PRD §X-Y（仮説 H\*/判断基準）— このタスクが無いと何が検証・達成できないか 1 文

## 達成すること

<このタスクが要件に対して果たす約束。1〜2 文>

## 最終挙動（Expected Behavior）

<マージ後に観察できる挙動を「X すると Y になる」の形で列挙。これがそのまま受け入れ条件の元になる>

- 例: `?from=announce` 付きで詳細ページを開くと、`profile_view` が `from=announce` で記録される
- 例: オファーが無い期間、詳細ページに空の区画が表示されない

## スコープ

### やること

### やらないこと（隣のタスク・将来に送るもの）

## 契約

- UI: <関係する props 型（モックの該当部分）>
- API/BFF: <interface-map の該当行>
- 計測: <イベント表の該当行>

## 受け入れ条件

- [ ] <最終挙動を gate・手元確認で判定可能な述語に降ろしたもの>

## 着手前に決めること

<未決があれば列挙。無ければ「なし」>

## PR 分割（1 PR に収まらない場合のみ）
```

## Step 5: 管理への落とし込み

- `docs/plans/<施策名>/plan.md`（時限）: 目的・チケット表・依存グラフ・期限からの逆算・レーン定義。**規約や方法論はここに書かない**（本スキルと規範 docs を参照する）
- GitHub: 統合 Issue ＋ ネイティブ sub-issue（1 チケット＝1 sub-issue、本文が正本）。ラベル（`決める`/`作る`/`手作業`）とマイルストーン
- **正本の一意性**: 同じ情報を 2 か所に置かない。設計＝docs／チケット詳細と状態＝Issue／全体像＝plan.md
- 並行規則: レーン（互いに契約を共有しない縦の列）単位で並行し、**レーン内は常に open PR 1 本**。DB migration を含む PR は生成順が衝突するため**着地順を決めて直列に**マージする
- PR 連携: 中間 PR は `Refs #N`、Issue を閉じる最終 PR だけ `Closes #N`

---

## 止まるべき地点

- Step 0 のゲートを満たさない要件を渡されたとき（分解せず要件整備を提案する）
- 契約・対応表に規範（`docs/product/` / `docs/architecture/`）に無い判断が必要になったとき — ドキュメント側を整える方向で相談（CLAUDE.md の規約）
- Step 3 の対応表はユーザーのレビュー・凍結を待ってから Step 4 に進む
- 「決める」種別のチケット（合意事項）が未決のまま、依存する実装チケットに着手しようとしたとき
